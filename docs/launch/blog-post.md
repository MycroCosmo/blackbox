# AI 에이전트는 왜 같은 에러를 5번 고칠까

> 초안. 모든 `<!-- BENCH -->` 자리표시자를 실제 벤치마크 수치로 채우거나 해당 문장을 지운 뒤 게시한다.
> 제목의 "5번"은 측정값이 아니라 흔히 보는 상황을 표현한 말이다. 본문에서도 그렇게 밝힌다.

에이전트에게 실패하는 테스트를 맡기면 이런 장면을 자주 본다. `NullPointerException`이 나면
스택 트레이스에 찍힌 줄에 null 검사를 넣는다. 다시 돌리면 같은 예외가 난다. 이번엔 바로 옆 줄을 고친다.
제목의 5번은 측정한 숫자가 아니다. 이렇게 맴도는 일이 드물지 않다는 뜻이다.

## 왜 맴도는가

세 가지 이유가 겹친다.

**첫째, 매 실행이 새것처럼 보인다.** 에이전트가 보는 건 방금 돌린 명령의 출력뿐이다.
"이 예외는 같은 자리에서 벌써 두 번째"라는 사실은 어디에도 적혀 있지 않다.
사람이라면 "아까 그거네" 하고 멈추겠지만, 에이전트는 매번 처음부터 분석한다.

**둘째, 로그가 너무 길다.** Gradle 테스트 출력은 수천 줄이 되기 쉽다.
컨텍스트를 아끼려고 `| tail -50`을 붙이면 끝부분만 남는다. 그런데 원인은 앞부분에
한 번만 찍히는 경우가 많다. Spring 컨텍스트 로딩이 실패하면 첫 테스트에서만 진짜 원인이
나오고, 나머지 수십 개 테스트는 "failure threshold exceeded"만 반복한다.

**셋째, 세션이 끝나면 다 잊는다.** 한 세션에서 알아낸 실패 맥락은 다음 세션으로 넘어가지 않는다.

## 실패에 이름과 기억을 붙이기

그래서 만든 게 [dev-blackbox](https://github.com/MycroCosmo/blackbox)다. 빌드·테스트 명령을
`npx dev-blackbox run -- ./gradlew test`처럼 감싸서 실행한다. 출력과 종료 코드는 그대로 두고,
실패하면 에러 타입, 정규화한 메시지, 최상단 애플리케이션 프레임을 묶어 fingerprint를 만든다.
줄 번호는 뺀다. 코드를 고치면 줄이 밀리는데, 그것 때문에 같은 실패가 새 실패로 보이면 안 되기 때문이다.

같은 fingerprint가 다시 나오면 기존 인시던트의 횟수를 올리고 출력 끝에 요약을 붙인다.

```text
✗ Command failed

Incident: INC-20260930-001
Type: PROCESS_FAILURE
Exit code: 1
Occurrences: 2
```

`Occurrences: 2`가 "아까 그거네"에 해당한다. 기록은 프로젝트의 `.dev-blackbox/`에 남기 때문에
다음 세션도 여기서 시작한다. Claude Code에서는 hook이 감싸지 않은 테스트 명령을 막고
dev-blackbox로 다시 실행하게 한다.

## 효과는 얼마나 되나

직접 만든 과제 3개로 A/B를 돌렸다. dev-blackbox 없이, 그리고 0.3.0 hook을 켜고 각 3회씩
`claude -p`로 실행해 입력 토큰, 테스트 실행 횟수, 같은 fingerprint 연속 실패, 통과 여부를 쟀다.

표본은 작고 과제도 내가 만들었다. 특히 Gradle 로그 과제는 원인이 로그 맨 앞에 있어서,
마지막 1,000줄만 보관하는 지금 버전으로는 잡을 수 없는 경우다. 결과가 불리해도 그대로 공개했다.
하네스와 개별 실행 결과는 저장소 `bench/`에 있으니 직접 돌려 볼 수 있다.

## 정리

에이전트가 맴도는 건 모델이 부족해서라기보다 실패에 대한 기억이 없어서인 경우가 많다.
실패마다 안정적인 이름을 붙이고 그 이름으로 반복을 세면, 적어도 "같은 걸 또 고치고 있다"는
사실은 에이전트에게 보여 줄 수 있다. 그다음 판단은 여전히 에이전트의 몫이다.
